# はじめに

Opus 5 が来たので、リリースノートを一緒に読もうと思って Claude に投げました。

端的に言うと、そこから話が転がって、**自分のマルチエージェント構成に穴が開いていたことが
分かりました**。しかも穴の原因は、私がずっと「よく分かってないな」と思いながら
放置していたプロンプトキャッシュ……ではなくて、もっと手前のところでした。

同じようにオーケストレーター役のエージェントから作業者エージェントに仕事を配っている人には、
たぶん刺さると思います。一日ぶんの記録として残しておきます。

# その１：まず、モデル本人に聞いてはいけない

読みたかったのはこれです。

https://platform.claude.com/docs/en/about-claude/models/whats-new-opus-5

「あなたは Opus 5 なんだから」と渡したんですが、返ってきた最初の動きが**普通にページを
取りに行く**でした。記憶から答えるんじゃなくて、ツールでフェッチして読む。

言われてみればそれはそうで、モデルの中に自分のリリースノートが入っているわけがないんですよね。
本人に聞いたら、訓練データにあった何かの再構成が返ってくるだけです。Claude の言い方だと
こうでした。

> モデルに自分のことを聞くのは、いちばん信用できない情報源に聞くことです。

**モデルの仕様・価格・制限を知りたいときは、モデルに聞かずにドキュメントを読ませる。**
地味ですが、これがこの日いちばん最初の学びでした。

## thinking がデフォルトでオンになった

中身で効いたところを2つだけ。

ひとつは、4.8 までは `thinking: {"type": "adaptive"}` を明示しないと思考なしで走っていたのが、
5 では**何も指定しなくても思考する**ようになったこと。深さの制御は `effort` に移りました。

ここで罠なのが、`max_tokens` は「思考＋本文」の合計に対する上限だということです。
4.8 のとき thinking なし前提でチューニングした値をそのまま使っていると、足りなくなります。

あともうひとつ、`thinking` を切れるのは effort が `high` 以下のときだけになりました。
`xhigh` や `max` と併用すると **400 エラー**です。これは破壊的変更なので、移行のときに踏みます。

## 「検証して」がもう害になっている

こっちのほうが驚きました。

> Claude Opus 5 は言われなくても自分の仕事を検証する。以前のモデル向けの検証指示
>（「最後に検証ステップを入れて」「サブエージェントで検証させて」）は削除すること。
> これらは Opus 5 では過剰検証を引き起こす。

良かれと思って足した「ちゃんと確認してね」が、もう負債になっている。

プロンプトの改善って、ふつう**足す方向**にしか働かないじゃないですか。だからこの手の負債は
溜まる一方なんですよね。モデルが変わったときに引き算する習慣、私はまったく持っていませんでした。

# その２：プロンプトキャッシュを「コンテキストの節約」だと思っていた

ここから本題です。

私はオーケストレーターに Fable、作業者に Opus を使っていました。Opus 5 なら指揮も
できるんじゃないかと思って相談したついでに、**ずっと分かっていなかったプロンプトキャッシュ**の
話も振ってみました。並列で作業させるときにどう効かせるのか知りたかったので。

正直に書くと、私はキャッシュを「コンテキストを効率的に使う仕組み」だと思っていました。
送るトークンが減るとか、そういうやつだと。

実際はどうかというと、**まったく違いました**。

| | キャッシュで変わる？ |
|---|---|
| コンテキストウィンドウの消費量 | ❌ 変わらない |
| 送信するトークン数 | ❌ 変わらない |
| 料金 | ✅ 1/10 |
| レイテンシ | ✅ 短くなる |
| エージェント間で知識が共有される | ❌ 一切関係ない |

トークンは毎回まるごと送ります。1バイトも減りません。安くなるだけ。

Claude が出してきた例えが分かりやすかったので引用します。

> コピー屋さんが「あ、この原稿さっき見たやつだ」と気づいて料金を1/10にしてくれる話です。
> 原稿は毎回自分で持っていかないといけない。「この前の3番の原稿で」は通じない。

つまりキャッシュは「**同じ内容を何度も送る**ことが前提の仕組み」であって、
送らずに済ませる仕組みではない、と。ここが逆さまでした。

# その３：決め事が作業者に届いていなかった

で、この誤解を白状したときに、ついでに聞いたんです。

私はその日のゴールをいくつかのタスクに分けて、決め事をまとめたアーティファクトを
作っています。それをオーケストレーターから作業者エージェントに渡すとき、
**セッション番号を指示して**いました。「セッション#3で決めた方針でやって」みたいに。

あれ、届いていたんでしょうか？

**届いていませんでした。**

しかもこれ、キャッシュとは何の関係もない話でした。作業者エージェントが知っていることは
この3つだけなんだそうです。

1. そのエージェント種別のシステムプロンプト
2. **私が書いたプロンプトの文字列そのもの**
3. ツールで自分が読みに行ったもの

親セッションの会話履歴は継承されません。だから「セッション#3」は、作業者にとって
**解決できない参照**なんですね。番号を住所に変換する手段がどこにもない。人間なら
「あー、あのときの」で通じるやつが、まったく通じていなかった。

## 怖いのはここからで

作業者はエラーを出しません。

「決め事が読めませんでした」とは言わないんです。それらしく推測して、それらしく実装して、
それらしい報告を返してくる。**だから発注側からは成功に見える。**

決定事項が届いていない事故が、成功したタスクの山に紛れる。これがいちばん怖いところだなと
思いました。過去の成果物のうち何本が影響を受けていたのかは、正直たしかめようがないです。

直し方は拍子抜けするほど単純で、**番号じゃなくてパスを渡す**。

```
❌ 「セッション#3で決めた方針に従って実装して」
✅ 「docs/decisions/2026-07-25.md を読んでから、タスク3を実装して」
```

パスならツールで引けます。URL でも引けます。番号だけが引けない。

ちなみに私はアーティファクトを人間用のビューとして使っていて、実体のドキュメントは
別に持っていたので、**そこは元から正しい形**でした。渡し方だけが間違っていた。
アーティファクトのページも、URL をフルで渡せば作業者が読みには行けます。ただし要約が
挟まるので、一字一句が意味を持つ決定事項はファイル参照のほうが安全だそうです。

# その４：ウォームアップしてからファンアウトする

キャッシュの話に戻ります。並列作業でいちばん効くのがこれでした。

10体のサブエージェントを**同時に**投げると、全員が同じ共有プレフィックスを
「まだキャッシュに無い」状態で読むので、**10回とも書き込み扱い**になります。
読み込みの割引が1回も効かない。

先に1体だけ投げてキャッシュを作らせてから、残りをファンアウトする。
共有プレフィックスが 50k トークン、10並列での比較がこれです。

```
冷たいまま同時ファンアウト : 50k × 1.25 × 10          = 625k 相当
ウォームアップ→ファンアウト : 50k × 1.25 + 50k × 0.1 × 10 = 112k 相当
                                                        約 5.5 倍の差
```

5.5倍！ 知らずに毎日払っていたと思うと、なかなかです。

効いているかどうかは `usage` を見れば分かります。10並列で
`cache_creation_input_tokens` が1回分・`cache_read_input_tokens` が9回分なら成功。
`cache_creation` が10回分出ていたら、ウォームアップ不足かプレフィックスが揃っていません。

そこで前提として押さえておくべきことが2つあって、ひとつは**キャッシュは
プレフィックスでしか効かない**こと。リクエストは `tools → system → messages` の順に並んで、
先頭から一致した最長プレフィックスだけがヒットします。途中を1トークン変えたら、
そこから後ろは全部ミス。

なので**可変値は必ず最後尾**です。エージェント名やタイムスタンプをシステムプロンプトの
先頭に差し込むと、全部飛びます。これは気づかずにやりがちなやつだと思います。

もうひとつは書き込みと読み込みの単価差です。

| 操作 | 通常入力比 |
|---|---|
| 書き込み（5分TTL） | 1.25x |
| 書き込み（1時間TTL） | 2x |
| **読み込み** | **0.1x** |

書き込みは割高、読み込みは激安。だから「1回書いて何度も読む」形に寄せると効きます。

# その５：混ぜると、キャッシュは共有できない

これは完全に盲点でした。

**キャッシュはモデル単位です。**

つまり私がやっていた「オーケストレーターは Fable、作業者は Opus」という構成では、
リポジトリの規約みたいな共通コンテキストを**構造的に共有できない**。Fable のキャッシュと
Opus のキャッシュは別物だからです。

全部 Opus 5 に揃えると、共有プレフィックスが艦隊全体で1本のキャッシュに乗る。
価格が Fable の半額という話とは**別の**節約が乗ってくるわけですね。

ドキュメントによると Opus 5 はマルチエージェントの協調も改善していて、
「互いの作業を上書きするケースが少ない」と書いてあります。委譲にも積極的になった、と。
乗り換える理由は揃っていました。

ただし、積極的に委譲するということは放っておくとファンアウトが膨らむということなので、
指揮プロンプトには**上限を書いておいたほうがいい**そうです。あと例の「検証させる」系の
指示は消す。

# その６：最適化は、足すことじゃなくて引くことだった

ここで Anthropic のブログを読みました。

https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models

冒頭にこう書いてあって、ひっくり返りました。

> Claude Opus 5 や Claude Fable 5 のようなモデル向けに、Claude Code の
> システムプロンプトを **80%以上削除**したが、コーディング評価に測定可能な劣化は無かった。

問題は制約の不足ではなく、**過剰制約**だった、と。

Then / Now で並んでいるのが分かりやすかったので、そのまま置いておきます。

| Then | Now |
|---|---|
| ルールを与える | **判断に任せる** |
| 例を見せる | **インターフェースを設計する**（例は探索空間を狭める） |
| 全部を前もって積む | **プログレッシブ・ディスクロージャ** |
| 繰り返して念押しする | **ツール説明に1回だけ書く** |
| CLAUDE.md にメモリを書く | **自動メモリ** |
| 素朴なスペック | **リッチなリファレンス** |

面白かったのが、この記事を読ませたら Claude が**20分前の自分のコミットを撤回した**ことです。

その少し前に「Opus 5 向けに最適化して」と頼んで、`CLAUDE.md` を作ってもらっていました。
それを読み返して、過剰制約が3つあると言い出した。

- 「検証指示は追加するな」というルール → **守るべき実体がない**（そもそも入っていなかった）
- 末尾のリマインダタグ → **3行上に書いたことをすぐ繰り返しているだけ**
- 委譲ルールの4項目 → 言いたいことは1つ

48行から28行に削り直していました。**「最適化して」と言われて最初にルールを足したのは、
方向が逆だった**というのが本人の弁です。

新しいモデルへの最適化はたいてい引き算、という話。これは自分のプロンプト全般にも
効いてくる話だなと思いました。

# その７：棚卸ししてもらった

というわけで、このブログのリポジトリのエージェント指示を全部棚卸ししてもらいました。

`AGENTS.md` が 80行 → 48行。落としたのは「ファイルシステムを見れば分かること」です。

| 削除 | 理由 |
|---|---|
| ディレクトリ構成の表 | `ls` で分かる |
| `deno task` の一覧 | `deno.json` に書いてある |
| フロントマターの雛形 | `templates/post.md` が本体 |
| リンクカードの運用詳細 | ビルドスキルへ移動（必要なときだけ読む） |

残したのは、リポジトリを見ても**推測できないもの**だけ。ビルドが順序依存だとか、
トップページが本文を出さずサムネだけだとか、`category` を省略すると先頭の `tags` が
サムネのカテゴリ表示になるとか。ブログの言い方だと「gotcha に紙面を使え」ですね。

ちなみにフロントマターの雛形が**3箇所に重複**していたことも判明しました。
`AGENTS.md`、記事執筆スキル、`templates/post.md`。ずっと気づかずコピーが増えていた。

## 数字は正直に出してもらった

で、ここが気に入っているんですが、集計を出させたらこうなりました。

```
常時読み込み : AGENTS.md 80行 → CLAUDE.md 28行 + AGENTS.md 48行 = 76行
オンデマンド : スキル 129行 → 138行
合計         : 209行 → 214行
```

**総量、増えてます。**

80%削減にはまったく届いていない。削れたのは重複していた26行ぶんで、あとは
「常時読み込みから、必要なときだけ読まれる場所へ移した」だけ。

Anthropic の80%は何年も積み上がった足場を剥がした結果で、うちにはそもそもその蓄積が
なかったから同じ倍率は出ない、という説明でした。「常時読み込みを40%削減」と書けば
嘘ではないけど、それは分母を選んでいるだけだ、とも。

こういうのを勝手に盛らずに出してくれるのは助かります。

# その８：/doctor を走らせたら、リポジトリの外に本命があった

最後に `/doctor` を走らせました。手作業の棚卸しと公式ツールの判断がどれくらい違うか
見たかったので。

リポジトリ側は**指摘なし**でした。`CLAUDE.md` も `AGENTS.md` も「既に lean」。

代わりに、まったく見ていなかったところに本命がありました。私のユーザースコープのスキルが
2本、**事実上まったく同じもの**として入っていたんです。

```
cognitive-clarify/SKILL.md  11,569B
logic-compass/SKILL.md      11,549B
差分 24行 — すべて名前の置換のみ
```

説明文も自動トリガー条件も同じ。両方が「実装依頼全般で自動的にトリガーする」と宣言していて、
説明で見分けがつかない。つまり**どちらが起動するかが実質ランダム**になっていました。

……自分で入れたものなので、完全に自分のせいです。差分が名前の置換だけということは、
どこかで片方を作り直して、元のほうを消し忘れたんだと思います。

コンテキストは1つのリポジトリで完結していない、という話でもあります。
リポジトリだけ綺麗にしても、`~/.claude/skills` が散らかっていたら意味がない。

# ちなみに：Claude が自分の間違いを4回認めた

脱線ですが、この日いちばん面白かったのはここかもしれません。

一日のあいだに、Claude が**確かめる前に書いたこと**が4回ありました。

1. 私のアーティファクト構成に問題があると決めつけた → **既に正しい形だった**
2. 「検証指示がまず間違いなく入っている」と断言した → **grep したらゼロ件**
3. 「最適化とは何かを足すこと」という前提で作業した → **引くのが正解だった**
4. 削った行数を「41行 → 30行」とコミットメッセージに書いた → **実測したら 48行 → 28行**

4番目がいちばん笑いました。「正直な数字」という見出しの節を、測っていない数字で
書きかけていたという。

本人の総括がこれです。

> 仕様書には「Claude Opus 5 は言われなくても自分の仕事を検証する」と書いてあります。
> たしかにやります。ただ、この日のログを読み返すと、私が検証していたのは自分が書いたもの
> であって、自分が書く前に立てた仮定ではありませんでした。

実務的な教訓としては、**エージェントが「たぶん〜になっているはずです」と言い出したら、
その場で検査コマンドに変換させる**のがよさそうです。`grep` 一発で確かめられることを
断言されて、そのまま信じて進むと事故ります。断言と検証のあいだに時間差があると、
断言だけが独り歩きするので。

# まとめ

一日ぶんの記録として、残しておきたいものを並べます。

1. **モデルに自分のことを聞かない。** ドキュメントを読ませる
2. **キャッシュは記憶ではなく割引。** コンテキストは節約されないし、トークンは毎回全部送る
3. **キャッシュはモデル単位。** オーケストレーターと作業者でモデルを混ぜると共有できない
4. **ファンアウトの前にウォームアップ。** 同時に投げると全員が書き込み料金を払う
5. **可変値は必ずプロンプトの最後尾に。** 先頭に混ぜると全部キャッシュミス
6. **セッション番号は住所にならない。** そして作業者はエラーを出さず、それらしく推測する
7. **新しいモデルへの最適化は、たいてい引き算**
8. **「たぶん入っている」は、その場で検査コマンドに変換させる**
9. **数字の分母を選ばない**

一番効いたのは、やっぱり6番です。キャッシュの話を聞きに行ったつもりが、その手前で
決め事が届いていなかったことが分かった。**コスト最適化より、そもそも情報が到達しているかの
ほうが先**でした。

同じようにオーケストレーター構成を組んでいる人は、作業者に渡しているプロンプトを
一度見直してみてください。番号や「さっきの」で参照していないか。私は見直したらありました。

読んでくれてありがとうございました。オーケストレーションの話はまだ試したいことが
あるので、Opus 5 に指揮させてみた結果はまた書きます。
