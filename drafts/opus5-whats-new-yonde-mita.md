# はじめに

端的に言うと、Claude Opus 5 の公式「What's new」を読んで、**自分の Claude Code 設定のほうを直した**話です。

https://platform.claude.com/docs/en/about-claude/models/whats-new-opus-5

新しいモデルが出たときって、だいたいベンチマークの数字と「すごい」の感想が先に流れてきます。でも自分みたいに個人開発でエージェントを常用していると、効いてくるのは数字よりも「既存の設定が壊れるかどうか」のほうなんですよね。実際このページには **破壊的変更** が 1 つ、しれっと書いてあります。

以下、前半はドキュメントに書いてあることだけ、後半は自分の環境で実際にやったこと、という順で書きます。混ぜないほうが後から自分が困らないので。

---

# ドキュメントに書いてあること

ここは公式ページの内容だけです。自分の解釈は次のセクションに分けました。

## 新しいモデル

API のモデル ID は `claude-opus-5`。**1M トークンのコンテキストウィンドウ**を持ち、ドキュメントによると 1M は既定であると同時に最大でもあって、**小さいコンテキストの派生モデルは存在しない**と書かれています。最大出力は 128k トークン、そして **thinking がデフォルトで ON**。

価格は入力 100 万トークンあたり $5、出力 $25 で、**Claude Opus 4.8 から据え置き**です。ドキュメントでは「Claude Fable 5 の半額でフロンティアの知性を提供する」という書き方をしています。

## 新機能

- **会話途中のツール変更（ベータ）** … セッション中にツールを追加・削除しても、プロンプトキャッシュを保ったままにできる。セッション開始時に固定したツール一覧を送り続けなくてよくなります。ベータヘッダは `mid-conversation-tool-changes-2026-07-01`。
- **fallbacks の `"default"` モード** … 自分で保守するモデルのリストではなく、Anthropic 推奨のフォールバックモデルを拒否カテゴリごとに当てる。`fallbacks` パラメータ全体がベータで、ヘッダは `server-side-fallback-2026-07-01`（1 つ前の `server-side-fallback-2026-06-01` は明示的なリストしか受け付けない）。
- **プロンプトキャッシュの最小長が短くなった** … キャッシュ可能な最小プロンプト長が **Opus 4.8 の 1,024 トークンから 512 トークンへ**。コード変更なしで、これまで短すぎてキャッシュできなかったプロンプトがキャッシュされるようになります。
- **Fast mode（リサーチプレビュー）** … Claude API のみで、Amazon Bedrock・Google Cloud・Microsoft Foundry では現時点で使えない。価格は入力 $10 / 出力 $50（100 万トークンあたり）。

## 挙動の変更

ここが本題です。

**その１：thinking がデフォルト ON**

Opus 4.8 では `thinking: {"type": "adaptive"}` を指定しない限り thinking なしで走っていたリクエストが、Opus 5 では同じリクエストのまま thinking ありで走ります。いつどれだけ考えるかはモデルが決め、その深さを制御するのが **effort パラメータ**です。ワイヤ上の値は変わっておらず、`thinking: {"type": "adaptive"}` は今も有効で、デフォルトと等価とのこと。

そして地味に大事な注意書きがあります。`max_tokens` は **thinking と応答テキストを合わせた出力全体のハードリミット**なので、4.8 で thinking なしで動いていたワークロードは見直せ、と。

**その２：effort の重みが増した**

`low` / `medium` / `high` / `xhigh` / `max` の 5 段階がすべて使えて、`max` が最も深い推論の最上位。デフォルトは `high` で、評価結果を見ながら上下させる（品質が保てるなら下げてトークンとレイテンシを節約、いちばん厳しい仕事では上げる）という運用が案内されています。`xhigh` や `max` で走らせるときは、サブエージェントやツール呼び出しをまたいで考え切れるよう **`max_tokens` を大きめに取れ**、とも。

**その３：thinking の無効化には effort `high` 以下が必要（破壊的変更）**

これが冒頭で書いた破壊的変更です。`thinking: {"type": "disabled"}` が受け付けられるのは **effort が `high` 以下のときだけ**で、`xhigh` や `max` と組み合わせると **400 エラー**が返ります。リクエストごとに強制される、Opus 5 以降の一般提供の挙動で、effort とは独立に thinking を切れた 4.8 からの破壊的変更だと明記されています。

対処は 2 択で、thinking を切ったままにするなら effort を `high` 以下にする、effort を維持するなら `thinking` フィールドを消す。

さらに、thinking を無効化した状態の Opus 5 は、**`tool_use` ブロックを出す代わりにツール呼び出しをテキスト出力に書いてしまったり、内部の XML タグが見える応答に混ざったりすることが稀にある**と書かれています。可能なら thinking は有効のままにして、トークンコストは effort を下げて制御するのが推奨です。

**その４：コードを変えなくても気づく挙動差**

- ユーザー向けの応答や成果物が既定で長くなる
- エージェント的なセッションで、進捗をユーザーに報告する頻度が上がる
- マルチエージェント構成で、サブエージェントに委譲しやすくなる
- **言われなくても自分の作業を検証する**

最後のやつには続きがあって、「最後に検証ステップを入れて」「サブエージェントを使って検証して」といった **前のモデルから引き継いだ検証指示は削除しろ**、Opus 5 では過剰検証の原因になる、と書かれています。

## 能力面

大きく伸びたところとして挙がっているのは、深い推論、エージェント的なコーディングと長時間タスク（スタブやプレースホルダを残さずに複数ファイルの機能を仕上げる）、テスト時計算のスケーリング、低い effort での効率、コードレビューとバグ発見、ビジョン、ロングコンテキスト、オフィス文書・スプレッドシート、マルチエージェント協調。

## 提供先と移行

Claude API（`claude-opus-5`）、AWS の Amazon Bedrock（`anthropic.claude-opus-5`）、Google Cloud、Microsoft Foundry。Opus 4.8 も引き続き全プラットフォームで利用できます。

移行はモデル ID を差し替えたうえで、上の 2 つの挙動変更（thinking デフォルト ON、`xhigh`・`max` での thinking 無効化が 400）を見直せ、という案内でした。

# ここから自分の話

## 同じ日に、Opus 5 限定のルール注入フックを入れていた

じつはこのページを読んだ日、自分は別件で **「Opus 5 で動いているセッションのときだけ、自作ルールをコンテキストに注入する」** 設定を `~/.claude/` に入れていました。

https://github.com/YasunaCoffee/semantic-generation-guard

Claude Code にはモデル別に設定を出し分ける公式機能がないので、`UserPromptSubmit` フックの中でモデルを判定して、Opus 5 系のときだけルールを標準出力に吐く、という力技です。判定は「環境変数 → トランスクリプトの最後の assistant メッセージが名乗るモデル ID → 起動コマンドの `--model` → settings の既定値」の順。

そこで実際に踏んだのが、**モデル ID の表記ゆれ**でした。ドキュメントに出てくる API のモデル ID は `claude-opus-5` ですが、Claude Code 側で 1M コンテキストを選んでいると、設定ファイルに保存される既定モデルは `opus[1m]` という表記になります。角括弧付きです。`claude-opus-5*` だけを見ていると、ここで素通りします。

なので判定はこう書きました。

```bash
case "$model" in
  claude-opus-5*|opus|opus\[*) is_opus5=1 ;;
esac
```

手元では `claude-opus-5` と `opus[1m]` で注入あり、`claude-sonnet-5` で無出力、同一セッションの 2 回目は無出力（`(session_id, model)` ごとに 1 回だけ注入）まで確認しました。**ドキュメントのモデル ID と、ツールが名乗るモデル ID は別物**という、当たり前だけど実際に動かすまで気づかないやつです。

ちなみにこの設定、最初の実装は `SessionStart` フックの stdin に入っている `model` フィールドで判定するつもりでした。でも実測したらペイロードに `model` は存在せず、**一度も発火していなかった**という。動かして確かめるまで気づけませんでした。

## 「検証指示を消せ」は、けっこう効く指摘

自分がいちばん刺さったのは、能力の話でも価格の話でもなく、**「前のモデル向けの検証指示を消せ」**でした。

エージェントを使い込むと、失敗するたびにプロンプトやルールに一行足す方向に進みがちです。「最後に検証して」「サブエージェントで確認して」あたりは、まさに自分が過去に足したやつでした。それがモデル側で標準装備になった結果、今度は**過剰検証としてコストになる**。足したルールを消すタイミングを持っていないと、設定はただ重くなっていきます。

そこで、自分の注入ルールのほうも「モデルがもうやることを書いていないか」という観点で見直しました。残したのは、モデル側の一般的な賢さでは埋まらないもの（自分の作品の位置づけラベル、自分が立てた区別、自分の環境の現行仕様）だけです。**汎用の丁寧さはモデルに任せて、固有の事情だけをルールに書く**、という切り分けに寄せた感じです。

## effort をどう置くか

自分の Claude Code の既定は `low` にしてあります。ドキュメントの推奨は「デフォルトの `high` から始めて評価で上下させる」なので、そこからは外れているんですが、日常の作業の大半は原稿の修正やファイル整理で、`low` でも十分品質が保てているのが実感です。ドキュメントにも「`low` と `medium` は、高い設定に比べてわずかなトークンとレイテンシで強い品質を出す」という書き方があって、そこは体感と合っていました。

で、上げるとしたらどこか。**`xhigh` や `max` を使うときは `max_tokens` を大きく取れ**という注意書きと、**thinking を切っていると 400 になる**という制約が、そのまま「上げるときのチェックリスト」になります。自分は Claude Code 経由での利用が中心なのでこの 400 を直接踏む場面は少ないですが、自作スクリプトで API を叩くほうには thinking を切っている箇所が残っているはずなので、そちらは effort を上げる前に確認が必要です。

## 1M コンテキストと「要約で落ちるもの」

1M が既定かつ最大、という割り切りは個人的にはうれしいところでした。ただ、長く持てることと、長い話が正しく残ることは別問題です。

自分は以前、過去のセッションログをまとめて調べたことがあって、そのとき見つかったズレのひとつが **「要約・圧縮のあとで構成の数量が消える」** というものでした。「4 分冊」という前提が圧縮後に消えて「1 冊にまとめる」で進行していた、みたいなやつです。コンテキストが伸びると、要約が走る回数自体は減ります。減りますが、走ったときに何が落ちるかは変わりません。ここは引き続きルール側で見張る領域だな、と思っています。

# まとめ

- Opus 5 は **thinking がデフォルト ON**。`max_tokens` は thinking 込みのハードリミットなので、4.8 の設定のままだと足りなくなる可能性がある
- **`xhigh` / `max` で `thinking: {"type": "disabled"}` は 400**。これが唯一の破壊的変更で、対処は「effort を下げる」か「`thinking` フィールドを消す」の 2 択
- プロンプトキャッシュの最小が **512 トークン**に。短いプロンプトがコード変更なしでキャッシュに乗る
- 価格は **$5 / $25 で据え置き**。Fast mode は $10 / $50 で Claude API のみ
- そして自分にとっての本題は、**前のモデル向けに足した検証指示を消す**こと

新機能を足す前に、前のモデル向けに書いた設定を引き算する。今回いちばん実務的だったのはそこでした。

同じようにエージェントの設定ファイルが育ちすぎている方は、一度「これ、もうモデルが勝手にやってない？」で読み直してみるといいかもしれません。
