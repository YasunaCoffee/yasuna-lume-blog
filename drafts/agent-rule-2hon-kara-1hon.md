# はじめに

端的に言うと、AI エージェント向けの自作ルールを **2 本入れて、同じ日のうちに 1 本削った**話です。

エージェントにルールを足すのは簡単です。失敗するたびに一行足せばいい。難しいのは**消すこと**で、消すにはまず「そのルールが効いているのか」を確かめないといけません。今回はそれを痕跡から確かめる方法が分かったので、その記録を書きます。

作ったものはこれです。

https://github.com/YasunaCoffee/semantic-generation-guard

# きっかけ：語を先に置いてしまう問題

もともとは、独自用語の乱立・曖昧化への対策として公開されていた semantic-generation skill / referent-before-label rule を読んだのがきっかけでした。**対象が曖昧なまま語を先に置いて、その語で思考を進めてしまう**問題への対策です。

読んで納得はしたんですが、そのまま写すのはやめました。**自分の環境で本当にそれが起きているのか分からなかった**からです。

そこで、手元のセッションログ（個人開発 3 リポジトリ、約 800MB）を実際に調べました。結果、**設計文書での造語はほとんど観測されませんでした**。代わりに繰り返し出てきたのは別の 6 パターンです。

1. **位置づけラベルのズレ** … 章とコラムを取り違えたまま実装完了まで走る
2. **区別の平坦化** … 採用案と没案、キャラクターと演者を一語にまとめてしまう
3. **定番パターンへの吸着** … 指定した描写を「よくある表現」に置き換える
4. **古い仕様の用語で現状を語る** … 変更前の仕様のまま説明を続ける
5. **主体・対象の勝手な推定** … 「別のエージェントが編集中」と断定（実際は自分）
6. **要約で構成と根拠が消える** … 「4 分冊」の前提が圧縮後に「1 冊」になる

自分がいちばん痛かったのは 3 番で、ギャグ描写を**定番の「鼻血」に置き換えられた**ことがあります。実際に指定したのは「牛乳をブーッとふく」でした。学習データ上の最頻パターンって、その場の正解とは限らないんですよね。

そこで、**元記事の rule を第二ルールとして残しつつ、実測から書いた 6 パターンを第一ルールにする**構成にしました。この時点でルールは 2 本です。

# Opus 5 のときだけ注入したい

ルールをコンテキストに載せるとトークンを食います。全モデルで常時載せるほどの確信はなかったので、**特定のモデルのときだけ注入する**ことにしました。

ところが Claude Code には、モデル別に設定を出し分ける公式機能がありません。そこでフックでゲートすることにしました。

## 最初の実装は一度も発火していなかった

最初は `SessionStart` フックの stdin に入っている `model` フィールドで判定するつもりでした。設計としては素直です。

でも実測したら、**ペイロードに `model` が存在しませんでした**。

```json
{"session_id":"...","transcript_path":"...","cwd":"...","hook_event_name":"SessionStart","source":"startup"}
```

判定は常に空振りで、ゲートは**一度も成立していませんでした**。動かして確かめるまで気づけないやつです。ドキュメントを読んで「あるはず」と思い込んでいた側の問題ですね。

そこで `UserPromptSubmit` に変えました。こちらは `transcript_path` をくれるので、**実際に応答しているモデル ID をトランスクリプトから読めます**。しかも毎プロンプト発火するので、セッション途中の `/model` 切り替えにも追従できる。副産物のほうが大きかったです。

登録はこれだけ。

```json
{
  "hooks": {
    "UserPromptSubmit": [
      { "hooks": [ { "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR/.claude/hooks/inject-semantic-rules.sh\"" } ] }
    ]
  }
}
```

モデル判定は確度の高い順に 4 段構えにしました。環境変数 `ANTHROPIC_MODEL` → トランスクリプトの最後の assistant メッセージが名乗るモデル ID → 起動コマンドの `--model`（`/proc` の祖先プロセスから取得）→ settings の既定モデル。特定できないときは**安全側に倒して注入しません**。

## `opus[1m]` という表記ゆれ

ここで踏んだのが表記の問題です。

公式ドキュメントに出てくる API のモデル ID は `claude-opus-5` です。でも Claude Code 側で 1M コンテキストを選んでいると、settings に保存される既定モデルは **`opus[1m]`** という表記になります。角括弧付きです。

`claude-opus-5*` だけを見ていると、ここで素通りします。

```bash
case "$model" in
  claude-opus-5*|opus|opus\[*) is_opus5=1 ;;
esac
```

**ドキュメントのモデル ID と、ツールが名乗るモデル ID は別物**。当たり前なんですが、実際に両方で試すまで気づきませんでした。

注入は `(session_id, model)` ごとに 1 回だけにしてあります。毎プロンプト再注入するとトークンがもったいないので。状態ファイルは `$TMPDIR/claude-semgen-guard/` に置きました。この状態ファイルが、後で効いてきます。

# 「どっちのルールが効いてるの？」

ここからが本題です。

導入後、実際にルールが入った状態でブログ記事を 1 本書かせてみました。手応えはかなり良くて、着手前に「これは下書きとして作ります」と位置づけを宣言してきたり、引用を要約せず原文のまま置いたりする。以前の失敗が再発しませんでした。

で、**ルールは 2 本ある**わけです。どっちが効いているのか。

## 痕跡で確かめる

聞いても意味がありません。モデルに「どのルールに従いましたか」と聞けば、それらしい答えが返ってくるだけです。なので**痕跡**を見ました。

まず注入されたかどうか。これは状態ファイルで分かります。

```console
$ ls -la "${TMPDIR:-/tmp}/claude-semgen-guard/"
-rw-rw-r-- 1 yasuna yasuna 13 Jul 26 13:09 a573095b-ea61-429f-8a8f-cb8ba69e92c0
$ cat "${TMPDIR:-/tmp}/claude-semgen-guard/a573095b-..."
claude-opus-5
```

セッション ID とモデルが記録されているので、**このセッションに注入が走った**ことは確定しました。

次に、どちらのルールが実際の行動に出たか。ここで決め手になったのが、**第二ルールが成果物を要求するルールだった**ことです。

第二ルールは「本文を 1 文字も書く前に、対応表（referent table）を独立ファイルとして保存する」を義務にしていました。つまり守ったなら `referent-table-*.md` というファイルが残るはずです。

```console
$ find . -name 'referent-table*'
（何も出ない）
```

**1 つも作られていませんでした。**

第二ルールには「判断できない場合は適用する」と書いてあります。ブログ記事は適用範囲外だと判断した、という言い訳は立ちますが、それにしても黙ってスキップされている。要するに、**コンテキストを消費しているだけで一度も発火していなかった**わけです。

一方、第一ルールのほうは行動に出ていました。

| 実際にやったこと | 対応する条 |
|---|---|
| 着手前に「下書きとして作ります」と 1 行宣言 | §1 位置づけラベルを勝手に決めない |
| 公式の記述と自分の感想を `---` で分離 | §2 区別を平坦化しない |
| 「MR は PR と受け取って進めます」と明記 | §5 推定は推定と明記 |
| 数値・パラメータ名を原文の表記のまま引用 | §6 引用・構成を落とさない |

## 削った

結論、**第二ルールを削除しました**。あわせて、対応表を作らせるための skill も外しました。あれは第二ルールを実行するためのものなので、残すと裏口から復活します。

念のため書いておくと、第二ルールの考え方が間違っているとは思っていません。**自分の環境では発火しなかった**というだけです。設計文書を大量に書く人なら効くかもしれない。

そして削除の判断ができたのは、**ルールが「ファイルを作れ」という形式だったから**でした。もし「よく考えろ」「丁寧に扱え」みたいな内面的な指示だったら、効いているかどうかを確かめる方法がありません。

ルールを書くときは、守ったときに**外から見える痕跡が残る形**にしておくと、あとで棚卸しできる。これが今回いちばんの収穫でした。

# 切り分けの限界

正直に書いておくと、この検証には穴があります。

- ルールを注入したセッションで、**私はインストール作業のついでにルール本文を全部読んでいる**。「注入されたから効いた」のか「読んだから効いた」のかは分離できていない
- 第一ルールは自分の失敗ログから作ったものなので、**過去の反省が入力に混ざっている**

きれいに測るなら、ルールを読んでいない新規セッションで、注入あり・なしを同じ依頼で走らせるしかありません。それはそのうちやります。

言えるのは「**第二ルールは、守っていれば必ず残るはずの成果物を 1 つも残していない**」という一点だけです。でも削除の判断にはそれで十分でした。

# 配れる形にする

最後に、ルールから個人名と作品固有の語を外しました。`yasuna-drift-patterns.md` → `drift-patterns.md` です。

ここで気をつけたのは、**実例の具体性を落とさないこと**でした。このルール自身が「実例のない禁則は守られない」と書いているので、抽象化しすぎると自分で自分を無効化してしまいます。

なので外したのは固有名詞だけです。

| 変更前 | 変更後 |
|---|---|
| yasuna の実セッションログ調査（manga / auto-aituber / utau） | 実セッションログの調査（個人開発の 3 リポジトリ、約 800MB） |
| 漫画・植字フロー | 制作物・既定の後工程フロー |
| 縦書き/横書き、付録範囲 | 組版方向、収録範囲、API のパラメータ名 |

「鼻血じゃなくて牛乳をブーッとふく」みたいな、読んだ人が一発で絵を思い浮かべられる実例はそのまま残しました。ここが抽象名詞になった瞬間に効かなくなると思ったので。

そのうえで「育て方」の節を足しました。**実例は自分の環境のものに差し替える前提**だと明記して、新しいズレを踏んだら 6 パターンのどれかに当てはめる、当てはまらなければパターンを 1 つ増やす、という手順を書いています。

# まとめ

- ルールは**足すより消すほうが難しい**。消すには「効いているか」を確かめる必要がある
- モデルに聞いても分からない。**痕跡で見る**。状態ファイルで注入の有無、成果物の有無で遵守の有無
- だからルールは、守ったときに**外から見える痕跡が残る形**で書いておくといい
- 実測から書いたルールは残り、**借りてきたルールは一度も発火しなかった**
- 抽象化するときも、**実例だけは自分の環境のものを残す**。実例のない禁則は守られない

ちなみに 2 本から 1 本に減らしたので、注入されるトークンは半分以下になりました。減らしたのに体感は落ちていません。まあ、そもそも片方は働いていなかったので当然なんですけども。

読んでくれてありがとうございました。ルールあり・なしの比較をちゃんと測ったら、また書きます。
